# Шифрование секретных данных — аудит и план (ноябрь-2026)

Продолжение `docs/AUDIT-ENCRYPTION-2026-10.md`. Проверено по коду и схеме; боевой сервер не видел. Ничего в данных не менялось — это план, шаги ниже выполняются только после явного «да».

## Что уже защищено (проверено)
- Тексты чатов, 2FA-секреты, реквизиты/адреса/документы (`*_enc`, `sealJson`), файлы (SKE1), копии в хранилище (SBK1, KEK отдельно) — как в аудите октября.
- Выданные ключи и ссылки: токены подтверждений (админка, SSH, хранилище, прямой доступ, заморозка, восстановление, QR-вход) лежат ТОЛЬКО хешами; секрет временного S3-ключа (`storage_direct_requests.secret_enc`) зашифрован и стирается при отзыве/истечении; OIDC-секреты клиентов — HMAC; резервные коды 2FA — HMAC.
- Единый журнал вырезает секреты (`scrub`), журнал хранилища скрывает поля `secret/token/key`.
- Секреты в git не лежат (`.env*` в `.gitignore`, в репозитории только `.env.example`/`.env.native`). Для `.env` на диске есть `scripts/env-seal.sh` (gpg AES-256).

## Найденные пробелы
| № | Область | Что | Риск |
|---|---|---|---|
| 1 | `.env` | работающие контейнеры держат секреты в окружении (`docker inspect`, root на хосте); `env-seal.sh` защищает только файл; неизвестно, включён ли он на боевом сервере | средний |
| 2 | `.env` | нет проверки «права 600, нет открытых копий, секреты не слабые» одной командой | низкий |
| 3 | База | `sky_ids.email/phone` открытым текстом (нужны для входа/поиска) | средний, принято ранее |
| 4 | База | `site_appeals.email`, `site_releases.email` открытым текстом (пробел №1 прошлого аудита, не закрыт) | средний |
| 5 | База | полные IP-адреса в журналах безопасности: `admin_gate`, `ssh_gate`, `device_links`, `account_freeze_log`, `recovery_*`, `device_approvals` (7 таблиц) | средний |
| 6 | Копии | `scripts/backup.sh` без `BACKUP_AGE_RECIPIENT` пишет ОТКРЫТЫЙ gzip-дамп (шифрование необязательное) | высокий |
| 7 | Ключи | `ENCRYPTION_KEY` один и без версий: нет ротации полей без остановки; нет защищённой копии ключа вне сервера (потеря = потеря данных) | высокий |
| 8 | Redis | пароль/закрытый порт/диск настраиваются вручную, из кода не проверяются | средний |

## План (по порядку, каждый шаг — с резервной копией и откатом)
1. **Копии (№6).** `backup.sh` в production отказывается писать без age-ключа (аварийный обход только явным `BACKUP_ALLOW_PLAIN=1` с предупреждением); `backup-verify.sh` проверяет расшифровку. Риск нулевой для данных.
2. **Аварийная копия ключей (№7, часть 1).** `scripts/key-escrow.sh`: выгружает `ENCRYPTION_KEY`, `STORAGE_KEK_*`, `JWT_SECRET` в файл, зашифрованный age/gpg паролем владельца, для хранения вне сервера; `--verify` проверяет, что файл открывается. Секреты не печатаются.
3. **Секреты не в окружении (№1).** Поддержка `<ИМЯ>_FILE` в `config.mjs` + `docker-compose` secrets для `JWT_SECRET`, `ENCRYPTION_KEY`, `STORAGE_S3_*`, `AI_API_KEY`: значения лежат файлами в tmpfs (0400) и не видны в `docker inspect`. Совместимо: прежние переменные работают как раньше.
4. **Проверка `.env` (№2).** `scripts/env-check.sh`: права, открытые копии/бэкапы, пустые и слабые секреты, наличие `.env.gpg`; только имена, значений не показывает.
5. **Версии ключей и ротация (№7, часть 2).** Префикс `v2` + связка `ENCRYPTION_KEYS` (старые ключи — только чтение), `scripts/rekey.mjs` с пробным проходом, проверкой обратной расшифровки и условной записью (как `seal-secrets`). Сначала пробный запуск и копия базы.
6. **Email обращений сайта (№4) и IP журналов (№5).** `*_hmac` для поиска + `*_enc`, запись в обе колонки, чтение с запасным вариантом, затем фоновое заполнение; в журналах безопасности вместо полного IP — HMAC-отпечаток и сеть /24 (для показа). Старые строки заполняются отдельной командой после проверки.
7. **Email/телефон Sky ID (№3) — ТОЛЬКО по отдельному решению.** Требует слепого индекса (HMAC) для входа и восстановления и переписывает все места, где читается почта (письма, 2FA, восстановление). Рекомендую пока НЕ делать: польза мала, регрессия по входу вероятна; вместо этого — ограничить доступ и журналировать выгрузки.
8. **Redis (№8).** `scripts/check-infra.sh`: проверяет, что порт Redis/Postgres закрыт снаружи и пароль задан; шифрование дисков — у хостера (LUKS), в отчёте отметить как ручной шаг.

## Что нужно от вас
- Пароль/ключ age для копий (публичный ключ, секретный храните вне сервера).
- Решение по пункту 7 (email/телефон Sky ID).
- Подтверждение, что на боевом сервере включён `env-seal.sh` (или включить).

## Откат
Все шаги добавочные: новые колонки/скрипты, прежнее чтение сохраняется («двойное чтение»); шифрование существующих данных — только после копии и проверки обратной расшифровки.
