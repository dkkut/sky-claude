# Аудит шифрования данных Sky (октябрь 2026)

Цель: честно показать, что и чем защищено, где пробелы и как их закрывать без риска потерять данные. Проверено по коду и схеме базы; **боевой сервер, диски и Redis хостера не проверялись** — что требует настройки у хостера, помечено отдельно.

## 1. Уровни защиты — это разные вещи

| Уровень | Что защищает | Что НЕ защищает |
|---|---|---|
| Канал (TLS, nginx) | содержимое запросов от чтения и подмены в пути | IP, время, объём соединений видны оператору/владельцу Wi-Fi |
| Диск сервера (LUKS/шифрование тома хостера) | украденный диск/снимок | работающий сервер, любой, кто вошёл на него |
| Объекты в хранилище (SKE1/SBK1) | файлы в S3 и копии при утечке бакета/копии | тот, у кого есть ключи (ENCRYPTION_KEY, KEK) |
| Поля базы (`encryptSecret/encryptContent`, v1.…) | утечку дампа БД без ключа | сервер, который ключ знает и обязан читать данные |
| Сквозное (E2EE) | содержимое даже от сервера | — |

**Sky сегодня НЕ сквозное шифрование.** Сервер расшифровывает сообщения и файлы (поиск, уведомления, модерация жалоб, Sky AI, вложения), поэтому называть защиту «E2EE» нельзя. Шифрование «в покое» защищает от утечки дампа БД, бакета и резервной копии, но не от того, кто владеет ключом на работающем сервере.

## 2. Инвентаризация

| Данные | Где | Защита | Вывод |
|---|---|---|---|
| Тексты сообщений, названия/описания чатов | БД, `encryptContent` (AES-256-GCM, ключ HKDF от `ENCRYPTION_KEY`) | шифруется в покое | ✔ (не E2EE) |
| Секреты 2FA (TOTP) | `sky_ids.two_factor_secret`, `encryptSecret` | шифруется; после настройки не показывается | ✔ |
| Пароль | `password_hash` | хеш (медленный) | ✔ |
| Коды входа/подтверждения, PIN при смене IP, токены ссылок (админка, SSH, заморозка, хранилище) | БД | только хеши (HMAC/SHA-256), токен — только в письме | ✔ |
| Реквизиты, адреса, документы (Market, GO, SkyKassa, логистика) | БД/диск | `*_enc`, `sealJson`, `mdf-` | ✔ |
| Файлы пользователей (музыка, кино, подкасты, книги, видео, вложения-файлы, Market, реклама и т.д.) | диск (`/data/*`) и/или S3 | SKE1: AES-256-GCM, DEK на файл, посегментно | ✔ |
| Резервные копии | S3/каталог копий | SBK1, KEK отдельно от ключей S3, ключи в архив не входят | ✔ |
| Секреты игр Sky Blox | `blox_games.secret_enc` | шифруется | ✔ |
| Ключ подписи вебхуков ботов | `bot_runtimes.webhook_secret` | **было открытым текстом → теперь шифруется** (запись) + миграция существующих | исправлено |
| Секреты QR-билетов | `tickets.qr_secret` | **было открытым текстом → теперь шифруется** + миграция | исправлено |
| Сырые отсканированные QR при неудачных сканированиях ПВЗ | `market_pvz_unmatched_scans.raw_token` | **хранился токен целиком → теперь отпечаток SHA-256 + длина** | исправлено |
| Email и телефон Sky ID | `sky_ids.email/phone` | открытым текстом — по необходимости (вход, поиск, письма) | принято; снижать видимость доступом и журналом |
| Email обращений с сайта (апелляции, релизы) | `site_appeals.email`, `site_releases.email` | **открытым текстом**, по ним ищется статус | **пробел**: план в п. 4 |
| Коды-приглашения чатов/игровых серверов | `chat_invites.code`, `game_servers.invite_code` | открытым текстом (это и есть «ссылка») | принято; срок и отзыв ограничивают риск |
| Журналы nginx | диск | **строки запроса и реферер с токенами в журнал больше не пишутся** | исправлено |
| Redis (сессии, лимиты) | память/диск Redis | без шифрования диска; в сессиях нет паролей, refresh-токен подписан | требует защиты Redis паролем и недоступности из сети |
| Временные файлы загрузки | диск | открытый файл на диск не пишется: поток шифруется «на лету» (`encryptStreamToFile`), незавершённое удаляется | ✔ |
| Скачиваемые архивы копий | потоком, на диск не кладутся | содержимое уже SBK1, ключей в архиве нет | ✔ |

## 3. Что сделано в этом проходе
1. Шифрование `bot_runtimes.webhook_secret` и `tickets.qr_secret` с **двойным чтением** (`openSecret` понимает открытое и зашифрованное): выкладка кода безопасна до миграции данных.
2. `scripts/seal-secrets.mjs` — миграция существующих значений: пробный проход по умолчанию, шифрование → обратная расшифровка → сверка → условная запись, идемпотентно. Перед `--apply` — резервная копия БД.
3. Отпечаток вместо сырого токена в журнале сканирований ПВЗ.
4. Журнал nginx без параметров запроса.
5. S3 только по https; API по открытому http не принимает данные.

## 4. Остающиеся пробелы и план (без необратимых шагов)
- **Email обращений с сайта**: добавить колонку `email_hmac` (HMAC для поиска) и `email_enc`, писать обе, читать с запасным вариантом, затем фоновое заполнение и только потом очистка открытой колонки. Не сделано.
- **Шифрование диска/тома сервера и Redis**: настраивается у хостера (LUKS/шифрованный том, `requirepass`, закрытый порт). Из кода не проверяется — проверить по инструкции хостера.
- **Сквозное шифрование личных чатов**: возможно только как отдельная режимная функция (секретные чаты) — тогда сервер не сможет искать, показывать превью в уведомлениях и подключать Sky AI в этих чатах. Требует протокола обмена ключами и хранения ключей на устройствах; для существующих чатов включать нельзя без миграции. Пока не внедрялось.
- **Потеря ключа**: `ENCRYPTION_KEY` и `STORAGE_KEK_*` не восстанавливаются. Хранить копии отдельно от сервера и от копий БД (см. DEPLOY.md). «Восстановление после потери ключа» возможно только из этой копии — иначе данные не открыть.
- **Ротация**: ключи медиа поддерживают список (старые остаются для чтения, `rewrapMediaKey` перепаковывает DEK); KEK копий — `setup-storage.sh --rotate`; общий `ENCRYPTION_KEY` меняется через `server/rekey.mjs` только после копии БД.

## 5. Как проверить
- `node scripts/seal-secrets.mjs` — сколько секретов ещё открытым текстом; `--apply` — зашифровать.
- `bash scripts/check-tls.sh web.<домен>` — канал.
- `node scripts/audit/secrets-seal-test.mjs`, `transport-test.mjs`, `skystorage-test.mjs`.
