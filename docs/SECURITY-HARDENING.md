## Результаты аудита
* Секреты в рабочем дереве и во всей истории git: **не найдены** (сканер, 9 шаблонов: ключи AWS/Google/Slack/GitHub, приватные ключи, JWT, пароли в URL, присвоенные секреты). Единственное упоминание `PRIVATE KEY` — проверка формата в `deploy.yml`.
* Отслеживаемые «чувствительные» имена: `.env.example` (заглушки), `.env.native` (публичные флаги, секретов нет) — это ожидаемо.
* `npm audit --omit=dev`: 0 уязвимостей.
* В `dist/` нет `.map` и ссылок `sourceMappingURL` (веб и `--mode native`).
* API-контейнер работает от пользователя `node`; `no-new-privileges` включён у api/postgres/redis; Postgres/Redis не публикуются наружу (`scripts/check-infra.sh`).
* Серверные секреты уже вынесены из `.env` в `secrets/*` (`scripts/secrets-to-files.sh`), данные шифруются слоем `crypto.mjs`, копии — `age`/SBK1, передача — TLS (`scripts/check-tls.sh`). Нового шифрования поверх этого не добавлялось.

## Что сознательно НЕ делалось и почему
* **Обфускация JavaScript** (javascript-obfuscator и т. п.): ломает размер/скорость и источники ошибок, не защищает бизнес-логику (она на сервере), в клиентском коде нет секретных алгоритмов. Минификация Vite/esbuild остаётся. Включать только отдельно, с полным прогоном UI-тестов на всех трёх целях.
* **R8/ProGuard для Android** (`minifyEnabled`): Capacitor-плагины и собственные (`AppIconPlugin`) используют рефлексию — без проверки на устройстве риск «тихой» поломки плагинов. Веб-часть и так внутри APK как минифицированные ассеты.
* **Шифрование файлов репозитория/каталога деплоя**: приложению нужно читать код; защита — права доступа, шифрование диска хостером (LUKS: `check-infra.sh` показывает, включено ли) и копии `age`.
* `cap_drop`/`read_only` для контейнеров, `no-new-privileges` для nginx: в этой среде нет Docker для проверки — применять на тестовом стенде.
* Переписывание истории git: не требуется (секретов нет); запрещено без явного решения владельца.

## Что делать владельцу на сервере (я не могу проверить из репозитория)
1. `bash scripts/check-infra.sh` и `bash scripts/env-check.sh` на боевом сервере; `chmod 700 /opt/sky /opt/sky/secrets`, `.env` — 600.
2. Репозиторий на GitHub: включить Secret scanning + Push protection и Dependabot (Settings → Code security), 2FA у всех участников, ветка защищена, доступ — минимально необходимый.
3. Включить шифрование диска у хостера; ключ `backup.key` держать вне сервера.
4. Первый деплой после этих правок: `deploy-local.sh` сам выполнит `nginx -t` на новом образе и остановится при ошибке (откат автоматический).

## Ротация секрета (если он когда-либо был раскрыт)
Порядок без простоя: (1) выпустить НОВЫЙ ключ у поставщика, не удаляя старый; (2) вписать новый в `.env`/`secrets/` (`scripts/set-*.sh`, `scripts/setup-*.sh`, `scripts/rotate-secrets.sh`); (3) `deploy-local.sh`; (4) проверить работу сервиса; (5) только затем отозвать старый. `ENCRYPTION_KEY` — особый порядок через `ENCRYPTION_KEY_PREV` и `scripts/rekey-all.mjs` (CLAUDE.md, «Ротация ENCRYPTION_KEY»). Если секрет попал в историю git: считать скомпрометированным, ротировать; историю не переписывать без решения владельца (план: `git filter-repo` на копии, принудительная публикация, пересоздание клонов).

## Откат
* Код: `git checkout pre-hardening-2026-10` или `git revert` нужного коммита; полный архив — `git bundle` (`git clone sky-pre-hardening.bundle`).
* Деплой: `deploy-local.sh` возвращает теги образов при неудачной проверке nginx; предыдущий образ остаётся на сервере.
* Android: `allowBackup` можно вернуть в `true` одной строкой манифеста.
