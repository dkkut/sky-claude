## API и права
- Обход всех адресов `/api/admin/*`, найденных в коде (94), всеми методами от обычного пользователя и анонима: 940 проверок, ни один 2xx/5xx (единственное исключение — статус шлюза `/api/admin/gate`, отдаёт `admin:false`). 3% ответов были 429 (лимитер) — они не маскируют результат (<5%, проверяется тестом).
- `rbac-test`: 73 административных адреса, одно замечание — `GET /api/moderation/flags` доступен любому вошедшему. **Принято как задумано**: это публичные метки контента (предупреждения/блокировки); идентификатор модератора для обычных людей вырезается (`contentflags.listFlags`).
- Адрес клиента везде через `clientIp()`; прямых `req.socket.remoteAddress` вне `http.mjs` нет.
- Статический обход SQL: склейки в запросах — только константы и закрытые словари (`TABLE[kind]` проверяется по `KINDS`); пользовательские значения идут параметрами.
- SSRF: исходящие запросы сервера — фиксированные хосты или адреса из конфигурации; адреса разработчиков игр — только через `bloxnet.mjs`.
- XSS: `dangerouslySetInnerHTML` используется для QR-SVG и наклейки поставки; в наклейке все поля экранируются. `eval`/`new Function` нет. `child_process` в server нет.
- Выдача вложений: строгий шаблон идентификатора, проверка членства, `nosniff`, CSP `sandbox`, `Vary: Authorization`.

## Админ-панель
Права на сервере у каждой операции; двухэтапный вход; деньги/Prime/подарки — заявки с подтверждением владельца и кодом; журнал администрации с цепочкой хешей; квитанции администратору о его действиях. Критические права хранилища не входят в `super_admin`. Регрессия `rbac`, `ws-authz` (12), `adminmoney` (29) — зелёная.

## Хранилище и база
- Медиа шифруются слоем `mediacrypto` (ключ `ENCRYPTION_KEY`), доступ — подписанные пропуски; S3 — только https. Резервные копии медиа — SBK1 (отдельный ключ KEK).
- **Риск (не исправлен, нужен план):** приложение подключается к PostgreSQL ролью `sky` = `POSTGRES_USER`, то есть **суперпользователем кластера**. При SQL-инъекции или захвате API это даёт чтение любых файлов и выполнение команд в контейнере БД (`COPY … PROGRAM`). Миграции выполняются самим приложением при старте, поэтому простая смена роли ломает деплой. План: (1) роль-владелец схемы `sky_owner` для миграций (одноразовый запуск), (2) роль `sky_app` без `SUPERUSER/CREATEDB/CREATEROLE` и с правами только DML на таблицы, (3) `DATABASE_URL` приложения → `sky_app`, миграции → `sky_owner`, (4) проверка на копии БД. Не выполнялось: требует окна деплоя и новых секретов.
- **Риск:** `scripts/backup.sh` делает копию БД без шифрования в локальный каталог (права 700) — при потере сервера копия пропадёт вместе с ним, при утечке диска прочитается; текст сообщений и секретные поля в БД зашифрованы на уровне приложения, остальное (профили, заказы) — нет. Рекомендация: шифровать дамп (`age`/`gpg`) и выносить на другой хост; восстановление из копии на тестовом окружении в этом аудите **не проверялось**.
- Журнал кошелька защищён триггером (миграция 162).

## Инфраструктура (только конфигурация репозитория)
- Наружу публикуются только 80/443 (nginx); API, PostgreSQL и Redis без `ports:`; у API, БД и Redis `no-new-privileges`.
- Заголовки: HSTS, `X-Frame-Options: DENY`, `nosniff`, строгая CSP (без `blob:` в `script-src`), COOP/CORP; для страниц ссылок из писем и сайта восстановления — `Referrer-Policy: no-referrer`; в журнал nginx не пишется строка запроса с токенами.
- API в production отвечает 426 на запрос по открытому http.
- Образ `certbot/certbot:latest` не закреплён по версии (низкий риск, воспроизводимость).
- Не проверялось: ОС сервера, SSH-конфигурация хоста, firewall, обновления, TLS боевого сертификата (`scripts/check-tls.sh` запускается на сервере), мониторинг, DDoS-защита.

## Зависимости
`npm audit --omit=dev`: 3 уязвимости (1 средняя, 2 высокие), все в цепочке `music-metadata-browser → music-metadata → file-type` (разбор тегов аудио в браузере при загрузке своего файла; типичное последствие — зависание на специально собранном файле). Исправление предлагается только через смену мажорной версии (понижение) — по договорённости (только патчи) **не применялось**. Риск: пользователь может «повесить» собственную вкладку.

## Подозрительная активность
Единый журнал событий с цепочкой хешей для `admin`/`security`, события `login_code_failed`, `refresh_reuse`, блокировки, пределы запросов, уведомления владельцу о заявках и действиях. В этом аудите добавлено событие `refresh_reuse`. Порогов-аномалий для финансовых операций (автоматическое ограничение) нет — только сверка баланса с журналом.

## Не проверено
Нагрузка и DDoS; боевые настройки; реальные платёжные провайдеры и почта/СМС; Android/Windows-сборки в боевых условиях; модули Market, GO, Blox, Garant, мессенджер/звонки не перечитывались построчно (опирались на их тесты и общие проверки); IDOR для каждого пользовательского адреса не перебирался автоматически (только админские).
